# sberpodbor-export

Выгрузка базы вашей компании из ATS **СберПодбор** (`api.sberpodbor.ru`) в локальный
файл SQLite. Один Node-скрипт, без сервера и без браузера: логинится вашим аккаунтом,
листает внутренний API и складывает всё в `sberpodbor.db`.

Что попадает в базу:

| Таблица | Что внутри |
|---|---|
| `profiles` | база кандидатов: ФИО, телефон, email, город, текущее место работы + сырой JSON |
| `vacancies` | вакансии: название, статус, город, сроки |
| `users` | сотрудники компании (авторы логов и комментариев) |
| `candidates` | заявки (профиль ↔ вакансия) со статусом, рекрутерами и менеджерами |
| `resumes` | последнее резюме профиля (HTML) и его источник (hh, linkedin, …) |
| `contacts` | контакты и соцсети из карточки кандидата |
| `logs` | история заявки: «прикреплён к вакансии», «изменён статус» и т.п. с автором |
| `comments` | комментарии к заявке с автором и датами |

Выгрузка **возобновляемая**: прогресс пишется в ту же базу, скрипт можно остановить
в любой момент и запустить снова, он продолжит с места остановки.

Карта эндпоинтов и замеренные ограничения API описаны в [API.md](./API.md).

## Требования

* Node.js 18 или новее (проверено на 24).
* Аккаунт в СберПодборе с правами на чтение профилей, вакансий и заявок.
* Для ускорения: несколько аккаунтов и по отдельному HTTP-прокси на каждый (необязательно).

## Установка

```bash
git clone https://github.com/Tkolin/sberpodbor-export.git
cd sberpodbor-export
npm install
cp accounts.example.json accounts.json
```

Откройте `accounts.json` и впишите свои аккаунты:

```json
[
  { "email": "a@example.com", "password": "...", "proxy": null },
  { "email": "b@example.com", "password": "...", "proxy": "http://user:pass@host:8080" }
]
```

* Каждый аккаунт становится отдельной «дорожкой» со своим токеном и своим IP.
  Работа делится между дорожками, все пишут в одну базу.
* `proxy: null` означает прямое соединение. Поддерживаются HTTP/HTTPS-прокси
  (CONNECT). SOCKS не поддерживается.
* Один аккаунт без прокси тоже работает, просто медленнее.

`accounts.json` уже в `.gitignore`. Не коммитьте его и не показывайте никому.

Вместо файла можно задать один аккаунт через переменные окружения
`SP_EMAIL`, `SP_PASSWORD` и необязательную `SP_PROXY`.

## Проверка перед стартом

```bash
node test-lanes.js
```

Для каждой дорожки печатает JSON: внешний IP через прокси, код ответа логина и
код ответа первого запроса к данным. Ожидаемо: `v2_login: 201`, `data_status: 200`
и `total` с числом профилей в вашей компании. Если логин отдаёт 401, см. раздел
про блокировку ниже.

## Запуск

```bash
node export.js
```

На Windows есть `run-export.cmd`: он запускает экспорт из папки скрипта с проверенными
настройками и пишет вывод в `run.log` / `run.err.log`.

Остановка: `Ctrl+C`. Повторный запуск продолжит выгрузку, ничего сбрасывать не нужно.
Чтобы начать заново, удалите `sberpodbor.db` (и файлы `-wal` / `-shm` рядом).

### Пробный прогон

Чтобы посмотреть на данные, не выгружая всё:

```bash
SP_MAX_PROFILE_PAGES=20 SP_DB=pilot.db node export.js
```

Скрипт возьмёт первые 20 страниц списка профилей (по 50 штук) и полностью обработает
только их. Фаза списка при этом не помечается завершённой, поэтому обычный запуск потом
доберёт остальное.

## Наблюдение за прогрессом

Оба дашборда открывают базу только на чтение, их можно запускать параллельно с экспортом.

```bash
node progress.js            # в терминале, обновляется каждые 5 секунд
node progress.js --once     # один снимок
node serve-progress.js      # веб-страница на http://localhost:8765 (порт: PORT=9000)
```

Показывают четыре фазы с процентами, скоростью и оценкой оставшегося времени,
плюс счётчики собранных записей.

## Настройка

Все параметры задаются переменными окружения.

| Переменная | По умолчанию | Что делает |
|---|---|---|
| `SP_DB` | `./sberpodbor.db` | путь к файлу базы |
| `SP_LANE_CONC` | `6` | одновременных запросов на один аккаунт |
| `SP_INTERVAL_MS` | `120` | минимальная пауза между стартами запросов на аккаунте |
| `SP_REQ_TIMEOUT_MS` | `30000` | таймаут одного запроса; зависший прокси иначе стоит по 5 минут |
| `SP_RELOGIN_MS` | `90000` | минимальный интервал между логинами одного аккаунта |
| `SP_BLOCK_MS` | `180000` | начальная пауза после блокировки, удваивается до 20 минут |
| `SP_MAX_PROFILE_PAGES` | `0` | ограничить число страниц списка профилей (0 = все) |

С тремя аккаунтами за отдельными прокси устойчиво работали `SP_LANE_CONC=14` и
`SP_INTERVAL_MS=100`. Поднимать параллельность выше смысла нет: сервер ограничивает
не число запросов, а латентность, и потолок около 4–5 запросов в секунду на аккаунт.

Тяжёлые фазы можно отключить в блоке `CONFIG` в начале `export.js`:
`fetchResumes`, `fetchContacts`, `fetchLogs`, `fetchComments`. Телефон, email, город
и текущее место работы приходят уже в списке профилей, так что `contacts` нужны в
основном ради соцсетей.

## Как это работает

Скрипт идёт по фазам, каждая фаза сохраняет чекпоинты и при перезапуске пропускает
уже сделанное.

| Фаза | Запросов | Что делает |
|---|---|---|
| `users`, `vacancies` | десятки | постранично, на первой дорожке |
| `profiles` | ≈ профилей / 50 | список профилей, страницы делятся между дорожками |
| `candmeta` | по одному на профиль | статусы заявок, рекрутеры, менеджеры |
| `details` | 2–4 на профиль | последнее резюме и контакты |
| `activity` | 2 на заявку | логи и комментарии; самая долгая фаза |

Полный обход компании с ~270 тысячами профилей это 0,6–0,8 млн запросов.
На одном аккаунте это около 50 часов, на трёх с прокси 15–18 часов. Запускайте
на машине, которая может работать сутками, или гоняйте по частям.

Если запрос окончательно не удался, запись **не** помечается сделанной и уходит
на следующий запуск. Ответ 403 считается окончательным «данных нет»: часть контактов
сервер не отдаёт никогда, и без этого правила такие профили откладывались бы бесконечно.

## Ограничения API, о которых надо знать

* **Один активный токен на аккаунт.** Новый логин убивает предыдущую сессию. Пока
  идёт выгрузка, **вас разлогинит в браузере**. Не работайте в веб-интерфейсе
  этим же аккаунтом параллельно со скриптом.
* **Блокировку вызывают частые логины, не объём данных.** Серия быстрых входов
  даёт 401 на все запросы. Скрипт логинится редко (токен живёт ~8 часов), при 401
  перелогинивается только та дорожка, чей токен реально протух, и делает паузу.
  Блок снимается полным входом через `POST /v2/auth/login`; если вы словили его
  вручную, просто подождите несколько минут.
* **Пагинация без предела.** Список профилей отдаёт любую страницу, обход по id
  не нужен.

Подробности и замеры в [API.md](./API.md).

## Работа с результатом

Открыть можно любым клиентом SQLite (`sqlite3`, DB Browser for SQLite, DBeaver).
В колонке `raw` каждой основной таблицы лежит исходный JSON ответа, если нужного
поля нет в колонках.

История заявок с автором и кандидатом:

```sql
SELECT p.last_name, p.first_name, c.vacancy_title, l.date_time_at, l.message, l.user_full_name
FROM logs l
JOIN candidates c ON c.candidate_id = l.candidate_id
JOIN profiles   p ON p.id = c.profile_id
ORDER BY l.date_time_at;
```

Комментарии по вакансии:

```sql
SELECT c.vacancy_title, p.last_name, p.first_name, m.created_at, m.user_full_name, m.comment
FROM comments m
JOIN candidates c ON c.candidate_id = m.candidate_id
JOIN profiles   p ON p.id = c.profile_id
WHERE c.vacancy_id = 12345;
```

Сколько уже собрано:

```sql
SELECT (SELECT COUNT(*) FROM profiles)   AS profiles,
       (SELECT COUNT(*) FROM candidates) AS candidates,
       (SELECT COUNT(*) FROM resumes)    AS resumes,
       (SELECT COUNT(*) FROM logs)       AS logs,
       (SELECT COUNT(*) FROM comments)   AS comments;
```

## Безопасность

* Пароли лежат в `accounts.json` открытым текстом. Файл в `.gitignore`, но храните
  его так же, как любой другой секрет, и смените пароли, когда выгрузка закончена.
* В логах скрипта прокси печатаются с замаскированным логином и паролем, а вот email
  аккаунтов видны. Не выкладывайте `run.log` целиком.
* Скрипт использует внутренний API СберПодбора, который не задокументирован публично
  и может измениться без предупреждения. Выгружайте только данные своей компании.
