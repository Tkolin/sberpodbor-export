# Сбер Подбор — выгрузка и админка

Сервис держит локальную копию базы Сбер Подбора в актуальном состоянии и даёт к ней
веб-интерфейс: управление аккаунтами обхода, просмотр данных, выгрузка в XML и
дашборд со статистикой.

```
nginx (TLS) ──┬── frontend   Nuxt 4 + Nuxt UI 4 + Unovis
              └── backend    FastAPI  ──┐
                 worker      обходчик ──┴── PostgreSQL 17
```

## Быстрый старт

```bash
cp .env.example .env      # заполнить секреты (как — написано внутри)
docker compose up -d
```

Панель открывается на `https://localhost`. Первый администратор создаётся из
`SP_BOOTSTRAP_ADMIN_EMAIL` / `SP_BOOTSTRAP_ADMIN_PASSWORD` — после первого входа
смените пароль и уберите переменную из окружения.

Сертификат в `nginx/certs/` самоподписанный. Для внешнего доступа положите туда
настоящий `fullchain.pem` / `privkey.pem`.

## Перенос старой базы SQLite

```bash
docker compose run --rm backend python migrate_sqlite.py \
  --src /legacy/sberpodbor-PRE-MIGRATION-20260907.db
```

Скрипт копирует данные через `COPY`, переносит отметки «уже собрано», сверяет
количество строк по каждой таблице и завершается с ненулевым кодом при расхождении.
Исходный файл открывается только на чтение.

## Как поддерживается актуальность

Полный обход — это 0,6–0,8 млн запросов и 40–55 часов, поэтому «всегда проверять»
устроено иначе. Воркер по кругу решает, что делать:

| Фаза | Когда | Что делает |
|---|---|---|
| `details` | есть профили без резюме | добирает резюме и контакты |
| `activity` | есть заявки без логов | добирает логи и комментарии |
| `sweep` | раз в час | перелистывает списки профилей, вакансий, сотрудников (~20 мин) |
| `rolling` | в свободное время | перепроверяет записи, которые дольше всех не сверялись |

Развёртка списков — ключ ко всему: строки списка профилей содержат `vacancies[]`
с `candidateId`, поэтому новые заявки обнаруживаются без единого обращения к
дорогим пер-кандидатным эндпоинтам.

Интервалы настраиваются: `SP_SWEEP_INTERVAL_MIN`, `SP_RECHECK_AFTER_DAYS`,
`SP_ROLLING_BATCH_SIZE`.

## Ограничения API, которые заложены в код

Это не абстрактные предосторожности — каждая стоила реального инцидента.

* **Один активный токен на аккаунт.** Повторный вход выбивает предыдущую сессию.
  Поэтому обход всегда один (`pg_try_advisory_lock` в воркере), а проверка аккаунта
  в админке отказывается работать во время синхронизации без явного подтверждения.
* **Блок вызывается частыми логинами, не объёмом данных.** При 401 повторный вход
  делает только тот воркер, чей токен действительно устарел; остальные подхватывают
  новый. Между логинами — не меньше `SP_MIN_RELOGIN_S`.
* **Сервер троттлит латентностью.** Потолок ~4–5 rps на аккаунт; выше параллельность
  только растит задержку. Значения по умолчанию (14 одновременных, интервал 100 мс)
  измерены как устойчивые.
* **403 — окончательный ответ, а не сбой.** Часть контактов сервер не отдаёт никогда.
  Такие записи закрываются с тем, что есть, иначе они откладываются бесконечно.
* **У всех запросов явный таймаут.** Зависший прокси иначе стоит по 5 минут на запрос
  и превращает сбой сети в тихий получасовой простой.

## Выгрузка XML

Схема — `backend/xsd/sberpodbor-export-1.0.xsd`, скачивается и из панели.
Профиль несёт вложенными контакты, резюме и заявки, а заявка — логи и комментарии.

* до 5 000 профилей — отдаётся сразу в браузер;
* больше — фоновая задача, файл складывается в `exports/`.

Текст экранируется, а не заворачивается в CDATA: резюме — произвольный HTML, а CDATA
не может содержать `]]>`. Символы, запрещённые XML 1.0, вырезаются.

## Роли

| Роль | Может |
|---|---|
| `admin` | всё, включая аккаунты ATS, пользователей и аудит |
| `operator` | просмотр, выгрузки, запуск синхронизации |
| `viewer` | только просмотр |

Пароли аккаунтов ATS и строки прокси шифруются Fernet-ключом `SP_ENCRYPTION_KEY` и
наружу не отдаются никогда — в интерфейсе прокси показывается замаскированным.
**Потеря ключа делает сохранённые учётные данные нечитаемыми**, храните его отдельно
от бэкапов базы.

## Разработка

```bash
docker compose up -d db
cd backend && pip install -r requirements.txt && alembic upgrade head
uvicorn app.main:app --reload

cd frontend && npm install && npm run dev
```

Миграции: `alembic revision --autogenerate -m "..."` внутри контейнера бэкенда.

## Старый экспортёр

`export.js` — исходный Node-обходчик, которым собрана первоначальная база. Он больше
не нужен для работы сервиса и оставлен как справочный материал: логика ротации токенов
и семантика ошибок перенесены в `backend/app/scraper/`.
